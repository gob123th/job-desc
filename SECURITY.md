# Security Setup & Notes

This document covers the security hardening applied to the JD app and the **manual
steps you must perform** in the Firebase console / Google Apps Script for it to take
effect. Code changes alone are not enough — Firestore rules must be deployed and the
admin account must exist.

---

## 1. What changed in the code

| Area | Before | After |
|------|--------|-------|
| Firestore rules | `read/write: if true` (wide open) | Locked: capability-URL reads, admin-only list, no public delete, validated create — see [firestore.rules](firestore.rules) |
| Admin login | Hardcoded `admin` / password in [js/admin.js](js/admin.js) | Real Firebase Email/Password Auth + email allowlist enforced in rules |
| Approval / Preview / Contract | Anyone with the link saw everything | Per-document access code (sent by email) gates the page — see [js/access-gate.js](js/access-gate.js) |
| Signature upload | No checks | Rejects non-images and files > 5 MB |
| Mail endpoint | `to` chosen freely by client | Harden the Apps Script (section 4) to whitelist recipients + rate-limit |
| Headers | none | CSP + `X-Frame-Options`, `nosniff`, `Referrer-Policy` via [firebase.json](firebase.json) (Firebase Hosting only) |
| Admin search | `.html()` with user input (DOM XSS) | `.text()` |

---

## 2. Firebase console steps (REQUIRED)

1. **Enable Email/Password auth**
   Firebase console → **Authentication** → **Sign-in method** → enable **Email/Password**.

2. **Create the admin account**
   Authentication → **Users** → **Add user** → enter the admin email + a strong password.

3. **Verify the admin's email** (rules require `email_verified == true`)
   Console-created users are *not* verified. Either:
   - have the admin trigger a verification email and click it, **or**
   - mark it verified with the Admin SDK / `gcloud`:
     ```
     # one-off, requires firebase-admin or gcloud auth
     firebase auth:import ...    # or use the Admin SDK updateUser({ emailVerified: true })
     ```
   Verification is what stops an attacker from self-registering an allowlisted email
   via the client SDK and granting themselves admin.

4. **Add the admin email(s) to the allowlist** in [firestore.rules](firestore.rules)
   inside `isAdmin()`, then deploy (next step).

5. **Deploy rules + hosting**
   ```
   firebase deploy --only firestore:rules
   firebase deploy --only hosting        # if you serve from Firebase Hosting (gets the headers)
   ```
   > Note: GitHub Pages cannot set custom headers, so the CSP/headers in
   > `firebase.json` only apply if you serve the site from Firebase Hosting.

## 3. How the per-document access code works

1. `index.html` generates an 8-char code, stores it on the document (`accessCode`),
   and emails it with the link.
2. `approval.html` (manager) prompts for the code before showing anything.
3. On approval, the same code is forwarded in the email to HR.
4. `preview.html` (HR) and `contract.html` prompt for the same code.
5. **A signed-in (verified) admin bypasses the prompt automatically** — so clicking a
   row in the admin console opens the document without asking for a code. This is why
   the four pages now also load `firebase-auth-compat.js`.

> The code is stored in plaintext, not hashed: because reads are capability-based (see
> the limitation below) a hash would add no real protection, and storing the plaintext
> lets the code be forwarded reliably between steps and shown in the admin's own view.

⚠️ **Limitation (important):** because this is a static site with **no backend**, the
code cannot be checked server-side. Anyone who has the document ID (the link) could in
principle read the raw document directly via the Firestore API and bypass the prompt.
The code + the unguessable 20-char document ID are **defense-in-depth**, not a hard
wall. The parts that *are* hard server-side guarantees: no collection listing, no
public delete, validated creates, and admin auth. See section 5 to make the code a
real server-side gate.

### ⚠️ The email must display the code (edit your Apps Script)

The frontend now sends an `access_code` field in the mail payload, **but the email body
is generated by your Google Apps Script**, so the code only appears once you add it to
the template there. Whatever template you use (plain text or HTML), include a line such
as:

```javascript
// inside doPost, when building the email body / HTML template:
var code = (body.access_code || '').toString();
// plain text:  'รหัสเข้าถึงเอกสาร: ' + code
// HTML:        '<p>รหัสเข้าถึงเอกสาร: <b>' + code + '</b></p>'
```

Then re-deploy the Apps Script as a new version. Until you do this, recipients get the
link but no code (which is the "no code shown" symptom).

## 4. Harden the mail endpoint (Google Apps Script)

The web-app URL and shared token in [js/mailjs-config.js](js/mailjs-config.js) are
visible in the page source, so the Apps Script **must** defend itself. Replace the
script's `doPost` with something like this:

```javascript
const SHARED_SECRET = '...';                 // must match token in mailjs-config.js
const ALLOWED = ['alisa@cclcolossal.com', 'alisa.cclcolossal@gmail.com']; // recipient whitelist
const MAX_PER_HOUR = 20;

function doPost(e) {
  try {
    const body = JSON.parse(e.postData.contents);

    // 1. Auth
    if (body.token !== SHARED_SECRET) return json({ ok: false, error: 'unauthorized' });

    // 2. Recipient whitelist — never send to an arbitrary client-supplied address
    if (ALLOWED.indexOf(body.to) === -1) return json({ ok: false, error: 'recipient not allowed' });

    // 3. Simple rate limit
    const cache = CacheService.getScriptCache();
    const key = 'cnt_' + Utilities.formatDate(new Date(), 'GMT', 'yyyyMMddHH');
    const n = Number(cache.get(key) || 0);
    if (n >= MAX_PER_HOUR) return json({ ok: false, error: 'rate limited' });
    cache.put(key, n + 1, 3700);

    // 4. Send (include the access code in the body)
    const code = (body.access_code || '').toString().slice(0, 16);
    GmailApp.sendEmail(body.to, body.subject, [
      'Requester: ' + body.requester_name,
      'Link: ' + body.review_url,
      code ? 'Access code: ' + code : ''
    ].join('\n'));

    return json({ ok: true });
  } catch (err) {
    return json({ ok: false, error: String(err) });
  }
}

function json(o) {
  return ContentService.createTextOutput(JSON.stringify(o))
    .setMimeType(ContentService.MimeType.JSON);
}
```

Re-deploy the Apps Script as a new version after editing. Consider rotating the shared
token if the current one may have leaked.

## 5. Optional upgrade — true server-side access gate (Cloud Functions)

To make the access code a real wall and fully lock down reads:

1. Upgrade the Firebase project to the **Blaze** plan (Cloud Functions require it).
2. Change `firestore.rules` so `job_descriptions` `get`/`list` are **`if isAdmin()`**
   only (deny anonymous reads entirely).
3. Add an HTTPS callable function `getDocument({ id, code })` that:
   - reads the doc with the Admin SDK,
   - compares `sha256(code)` to the stored `accessHash`,
   - returns the document only on match (and rate-limits attempts).
4. Point `approval.js` / `preview.js` / `contract.js` at the callable instead of
   reading Firestore directly.

This removes the static-site limitation in section 3.

---

## 6. Reminder: the Firebase `apiKey` is not a secret

The `apiKey` in [js/firebase-config.js](js/firebase-config.js) is meant to be public;
it only identifies the project. All real protection comes from **Firestore rules +
Auth** above — never rely on hiding the API key.
